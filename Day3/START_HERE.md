# تمرین ۳: از API تا پاسخ مستند (راهنمای شروع)

این بسته همهٔ داده‌ها و ابزارهای لازم برای تمرین جلسهٔ سوم را دارد. سؤال‌ها و محل ثبت پاسخ‌ها در سایت است (صفحهٔ «تکلیف ۳»)؛ فرم HTML جدا وجود ندارد، چون با حساب خودت وارد شده‌ای و پاسخ‌ها همان‌جا ذخیره می‌شوند.

## چه چیزی داخل بسته است

| پوشه یا فایل | کاربرد |
|---|---|
| `Day3_Datasets/` | هفت مجموعه داده و دو PDF آزمایشی؛ مسیر داده هر بخش جلوی همان بخش در سایت آمده است |
| `Day3_Grading/` | `check_day3_db.py`: بررسی‌گر خودکار دیتابیس (همان که پس از ارسال روی فایل تو اجرا می‌شود) و قرارداد جدول‌ها |
| `Day3_Resources/embedding_model_manifest.json` | نسخهٔ دقیق و hash مدل embedding (خود مدل در بسته نیست، پایین‌تر دانلود می‌شود) |

## ۱. محیط پایتون

## ۲. مدل embedding (حدود ۹۰ مگابایت)

مدل `sentence-transformers/all-MiniLM-L6-v2` با نسخهٔ ثابت زیر را یک بار دانلود کن و مسیر آن را در نوت‌بوک بده. بعد از دانلود، اجرا نیازی به اینترنت ندارد.

```python
from huggingface_hub import snapshot_download
path = snapshot_download("sentence-transformers/all-MiniLM-L6-v2",
                         revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41",
                         local_dir="Day3_Resources/embedding_model")
```

مدل انگلیسی است؛ کیفیت فارسی در این تمرین سنجیده نمی‌شود. تحلیل‌های خودت را فارسی بنویس.

## ۳. دیتابیس: یک فایل SQLite

لازم نیست Docker، PostgreSQL یا رمزی داشته باشی. دیتابیس یک فایل به نام `day3.sqlite` است که با کتابخانهٔ استاندارد `sqlite3` پایتون می‌سازی. جدول‌ها، کلیدهای خارجی و داده‌ای که باید داشته باشد در `Day3_Grading/README.md` آمده است. یادت باشد در هر اتصال `PRAGMA foreign_keys=ON` را اجرا کنی، وگرنه SQLite کلید خارجی را اعمال نمی‌کند. بردارها را در ستون `embedding` به‌صورت BLOB (۳۸۴ عدد float32) یا متن JSON نگه دار.

پیش از ارسال، فایل خودت را امتحان کن:

```sh
python Day3_Grading/check_day3_db.py day3.sqlite
```

هر خط `OK` یا `FAIL` است و در پایان وضعیت `passed` یا `failed` می‌آید. دقیقاً همین بررسی پس از ارسال روی فایلی که بارگذاری می‌کنی اجرا می‌شود و نمرهٔ بخش اجرایی سؤال‌های دیتابیس از روی آن است؛ پس هر `FAIL` را همین حالا درست کن.

## ۴. نوت‌بوک: قالبی که ایجنت تصحیح می‌تواند دنبال کند

نوت‌بوک را تمیز اجرا کن (Restart Kernel و Run All) تا خروجی سلول‌ها ذخیره باشد. برای **هر زیرسؤال سه سلول** بساز، با همین ترتیب:

1. **Markdown**، با عنوان `زیرسؤال ۵٫۳` (شمارهٔ همان زیرسؤال) و صورت سؤال. همین عنوان است که تصحیح‌کننده برای پیدا کردن کد و خروجی هر سؤال می‌خواند؛ بدون آن، بخش عملی آن سؤال کم نمره می‌گیرد.
2. **Code**، کد انگلیسی و قابل اجرا که خروجی را چاپ می‌کند (بذر مرجع `20261015`).
3. **Markdown فارسی راست‌به‌چپ**، تحلیل: چه کردی، عدد چه می‌گوید، محدودیت چیست.

عددهایی که در سایت می‌نویسی باید همان‌هایی باشند که در خروجی نوت‌بوک چاپ شده‌اند. زمان و تأخیر به دستگاه بستگی دارد و با عدد مرجع تطبیق سخت داده نمی‌شود.

## ۵. فایل‌هایی که بارگذاری می‌کنی (چهار فایل)

| فایل | محتوا |
|---|---|
| نوت‌بوک اجراشده `.ipynb` | همان نوت‌بوک کامل با خروجی‌ها |
| `day3.sqlite` | دیتابیس نهایی با جدول‌ها، ۲۰ کاربر، ۱۲۰ پرونده، اسناد و chunkهای دارای بردار. بدون رمز یا اطلاعات شخصی |
| `test_predictions.jsonl` | برای هر پرسش test یک خط: `{"query_id": "...", "ranked_doc_ids": ["PEP-0498", "PEP-0343", "PEP-0572"]}` (سه سند متمایز) |
| `answerability_predictions.jsonl` | برای هر پرسش test یک خط: `{"query_id": "...", "score": 0.63, "accepted": true}` |

تنظیمات (روش بازیابی، آستانه) را فقط با train و dev انتخاب کن و پیش از ساختن فایل‌های test قفل کن. test فقط برای سنجش نهایی است و برچسب آن نزد مدرس می‌ماند.

## ۶. تصحیح چطور کار می‌کند

- هر زیرسؤال مفهومی: ۶۰٪ گزینه و ۴۰٪ دلیل. هر زیرسؤال عملی: ۶۰٪ کد و نتیجهٔ بازتولیدپذیر و ۴۰٪ تحلیل متناسب با شواهد. نمرهٔ هر سؤال کنار آن آمده و جمع ۱۰۰ است.
- گزینه‌ها، فایل‌های پیش‌بینی و بخش اجرایی سؤال‌های دیتابیس با کد سنجیده می‌شوند؛ دلیل‌ها و تحلیل‌ها را ایجنت تصحیح می‌خواند و با نوت‌بوک تو تطبیق می‌دهد. هیچ‌چیزی که بارگذاری می‌کنی اجرا نمی‌شود: نوت‌بوک فقط خوانده می‌شود و فایل دیتابیس فقط باز و بررسی می‌شود.
- هرچه در پاسخ دربارهٔ وضعیت یا شمار بررسی دیتابیس می‌نویسی با نتیجهٔ بررسی خودکار روی فایل بارگذاری‌شده مقایسه می‌شود.
- استدلال درست دربارهٔ شکست مدل یا محدودیت داده نمره دارد؛ metric بالا به‌تنهایی هدف نیست.

## ۷. مرز اجرا

پاسخ HTTP ارائه‌دهنده، توکن هویت، حمله‌ها و داده‌های کاربران همه مصنوعی (fixture) هستند. ورود زندهٔ Google، LLM پولی، PostgreSQL و استقرار اینترنتی لازم نیست. در گزارش‌ات «واقعاً اجراشده»، «fixture» و «اجرا‌نشده» را جدا بنویس و بیش از شواهد ادعا نکن.
